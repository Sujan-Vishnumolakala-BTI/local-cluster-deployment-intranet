# 08 — Monitoring

## Overview

This project uses **Prometheus** and **Grafana** to monitor the Kubernetes cluster.

The monitoring stack provides:

* Kubernetes cluster metrics
* Node CPU and memory metrics
* Pod and container metrics
* Kubernetes object state
* Control-plane monitoring
* Alertmanager integration
* Grafana dashboards
* Persistent storage for Prometheus data
* Persistent storage for Alertmanager data

The recommended deployment method for this project is the **kube-prometheus-stack** Helm chart.

The stack includes:

* Prometheus Operator
* Prometheus
* Grafana
* Alertmanager
* Node Exporter
* kube-state-metrics
* ServiceMonitor and PodMonitor support

---

# 1. Monitoring Architecture

```text
                         Kubernetes Cluster
                                |
              +-----------------+-----------------+
              |                 |                 |
          Master 01         Master 02         Master 03
              |                 |                 |
              +-----------------+-----------------+
                                |
                         Worker Nodes
                      +---------+---------+
                      |         |         |
                   Worker01  Worker02  Worker03
                      |         |         |
                      +---------+---------+
                                |
                         Monitoring Stack
                                |
             +------------------+------------------+
             |                  |                  |
         Prometheus          Grafana          Alertmanager
             |                  |
             |             Dashboards
             |
       Metrics Collection
             |
      +------+-------+-------+
      |      |       |       |
   Node    Pods   kube-state  API
  Exporter         Metrics   Server
```

Prometheus collects metrics and stores them as time-series data.

Grafana queries Prometheus and displays the collected metrics through dashboards.

Alertmanager handles alerts generated by Prometheus.

# 19. Persistent Storage

Prometheus stores time-series data on disk.

For a production-style cluster, persistent storage should be used instead of relying only on the pod filesystem.

The project already uses OpenEBS for storage.

The monitoring architecture can therefore use:

```text
Prometheus
    |
    v
PersistentVolumeClaim
    |
    v
OpenEBS StorageClass
    |
    v
PersistentVolume
    |
    v
OpenEBS Storage
```

Check available StorageClasses:

```bash
kubectl get storageclass
```

Select the OpenEBS StorageClass appropriate for the storage engine configured in the cluster.

Do not assume that every OpenEBS StorageClass provides the same replication, failure handling, or topology behavior.

---

# 20. Monitoring Storage Requirements

Prometheus storage requirements depend on:

* Number of nodes
* Number of pods
* Number of metrics
* Scrape interval
* Retention period
* Number of applications
* Number of ServiceMonitors
* Number of PodMonitors

For this project, an initial Prometheus PVC of approximately:

```text
20Gi
```

can be used as a starting point.

The required capacity should be adjusted after observing actual metric ingestion and retention.

---

# 21. Prometheus Retention

Prometheus retention controls how long historical metrics are stored.

Example:

```text
7 days
```

Longer retention requires additional storage.

A basic design is:

```text
Retention: 7d
Storage: 20Gi
```

This is a starting configuration, not a universal sizing rule.

Monitor the filesystem and PVC utilization regularly.

# 25. CPU Monitoring

Example PromQL query:

```promql
100 * (
  1 - avg by(instance) (
    rate(node_cpu_seconds_total{mode="idle"}[5m])
  )
)
```

This can be used to visualize approximate node CPU utilization.

For container CPU:

```promql
sum by (pod) (
  rate(container_cpu_usage_seconds_total[5m])
)
```

---

# 26. Memory Monitoring

Available node memory:

```promql
node_memory_MemAvailable_bytes
```

Memory usage can be derived from:

```promql
100 * (
  1 -
  node_memory_MemAvailable_bytes /
  node_memory_MemTotal_bytes
)
```

Use Grafana to display memory usage over time.

---

# 27. Disk Monitoring

Check available filesystem space:

```promql
node_filesystem_avail_bytes
```

Filesystem size:

```promql
node_filesystem_size_bytes
```

Example utilization query:

```promql
100 * (
  1 -
  node_filesystem_avail_bytes /
  node_filesystem_size_bytes
)
```

Disk monitoring is particularly important because Prometheus, Loki, container images, logs, and OpenEBS volumes all consume storage.

# 29. Monitoring etcd

Because etcd is part of the control plane, etcd health should also be monitored.

Important etcd indicators include:

```text
Leader availability
Database size
Commit latency
Disk WAL latency
Request rate
Backend commit duration
```

Manual health check:

```bash
ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  endpoint health
```

The exact certificate arguments depend on the kubeadm-generated etcd certificates.

For example:

```bash
ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/peer.crt \
  --key=/etc/kubernetes/pki/etcd/peer.key \
  endpoint health
```

Use the correct certificate set for the operation being performed.

# 30. Monitoring Architecture with Logging

Monitoring and logging are separate systems.

```text
                 Kubernetes Cluster
                         |
          +--------------+--------------+
          |                             |
      Metrics                         Logs
          |                             |
      Prometheus                      Fluentd
          |                             |
       Grafana                         Loki
          |                             |
     Dashboards                     Log Queries
```

Prometheus should not be used as a log storage system.

Loki should handle log storage and querying.

Grafana can provide a common visualization layer for both Prometheus and Loki.

# 33. Monitoring Security

Do not expose Prometheus or Grafana directly to the public Internet without appropriate security controls.

Recommended approach:

```text
User
  |
  v
Authenticated Access
  |
  v
Grafana
  |
  v
Prometheus
```

For a local cluster, `kubectl port-forward` is sufficient for initial access.

For a shared environment, use an authenticated ingress or another controlled access mechanism.
